# M1 loop

A loop is a plan run by agents with the session as manager. This page is
the loop's contract; the plan (`m1-sale-and-ticket-on-one-desktop`) holds
the tasks and their statuses; the ledger on the WSL box
(`~/.dz-night/ledger.md`) holds the ticks. `loops` is a new domain for
pc-ctx: the CLI and the MCP do not know it yet (idea logged); until then
it is a page with frontmatter, read by hand.

## Roles

- Session (Fable): manager. Writes briefs, spawns, rebases, runs the
  main-checkout gates and e2e, runs review Pass 2, merges, ticks, updates
  the plan and the report site. Never implements while agents run, except
  a one-line fix on a merge conflict.
- Implementation agent: one task, one worktree under
  `.claude/worktrees/<task>`, one branch `m1/<task>`. Red-first tests,
  `just gates` before every push, e2e with its own port pair. Reports in
  the shape `~/.dz-night/briefs/common.md` fixes. Kept alive after its
  report so review findings go back to the same agent.
- Review agent: read-only, one lens (dz-review), on a finished branch.
- Samir: opens checkpoint PRs (`/dz-pr m1/2026-09-09`), merges them, runs
  T6 at the printer, answers the questions the ticks raise.

## Waves

| Wave | Tasks | Why together |
|---|---|---|
| 1 | T3 documents + sale service, T7 three languages + RTL, T8 backup + restore | disjoint code (core/API; desktop shell and i18n; core backup + a settings panel) |
| 2 | T4 till screen (needs T3), T5 ticket template (needs T3's document) | both read the document model; T5 can start on T3's branch head before T4 finishes |
| 3 | stale-check sweep, progress report, checkpoint PR at T8 | closes M1 except T6 |

Four agents at once at most: three implementers and one reviewer, or two
and two. RAM is the bound (11 GB): agents build with `CARGO_BUILD_JOBS=4`
and each worktree has its own target dir.

## Model per job

| Job | Model | Reason |
|---|---|---|
| Money, ledgers, numbering, auth, file swaps (T3, T4, T8, Pass 2 lenses on centimes and reach) | opus | a wrong centime or a lost number costs more than the tokens |
| UI mechanics, i18n, RTL, screenshots, docs sweeps, report pages (T7, prose lens, stale-check) | sonnet | bounded, pattern-driven work |
| Counting, listing, port checks, log tails, one-file lookups | haiku | no judgement needed |
| Golden files for printed documents (T5) | opus for the template and the fr/en words; the Arabic stays disclosed as unreviewed until a native speaker reads it | |

## Checks every branch passes, in order

1. Agent: red-first tests, `just gates` green in the worktree, e2e with its
   ports when the desktop changed, report with counts and log tails.
2. Session: rebase the branch on the milestone head (`git rebase
   m1/2026-09-09`), rerun `just gates` in the main checkout, `just e2e` in
   the main checkout (the shared suite, all languages once T7 lands).
3. Review: dz-review lenses on the diff. Full Pass 2 (proof by running,
   not reading) on T3 and T4; one lens on the rest. Findings go back to
   the same agent with a message; the fix round gets the same lens on the
   fix diff.
4. Merge `--no-ff` into `m1/2026-09-09` with the `ctx:` trailer; push;
   plan task status; ledger tick.
5. After two merges in a row, a whole-suite run on the milestone head
   before the next merge (two green branches can be red together).
6. Checkpoint PRs to `main` at T4 and T8: Samir opens, CI is the first
   external run of the milestone branch, `stale-check` runs after the
   merge, one progress page on the report site per checkpoint.

## Ticks

- Event ticks: launch of a wave, each agent report, each review verdict,
  each merge, each checkpoint. Written to the ledger within the same
  step, one paragraph, with log file names.
- Heartbeat: every 10 minutes while agents run (Samir, 2026-09-09: 30 was
  too long), one line with which agents run and since when, the newest
  commit on each branch, and free disk, so a resumed session knows the
  loop was alive and where each branch stood.
- Samir-facing: one short message per wave (launch and close), and at any
  blocker that needs him (printer, PR, a fiscal question).

## Stop conditions

- An agent reports a gate it could not make green: the session takes the
  branch, reads the log, decides fix or defer; never merges red.
- Two agents change the same file in conflicting ways: the later branch
  is rebased and re-gated; if the conflict is a design disagreement, the
  session rules, writes the ruling in the tick, and the loser's agent
  adapts.
- Disk under 20 GB or a cargo OOM: no new agent until a worktree is
  removed.
- A finding that changes a fiscal rule: stop the wave, write the question
  for the comptable in `docs/features.md`, continue on the assumption
  marked as such.

## What pc-ctx needs for loops (later)

A `loops` category with `plan` in the frontmatter, `ctx loop show <slug>`
printing the waves with the tasks' live statuses from the plan, and a
`tick` entry type so the ledger can move from the WSL box into
`context/`. Logged as an idea; not blocking.
